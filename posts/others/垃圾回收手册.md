# 垃圾回收手册

本文基于该书进行进一步扩展，并给出一些个人总结

## 第一章 介绍

几乎所有的现代编程语言都是用动态内存分配，这使得对象可以在其总大小在程序编译时未知的情况下被分配和释放，并且如果它们的生命周期可能超过分配它们的子程序的激活的生命周期。动态分配的对象存储在堆中，而不是栈中。

使用堆分配尤其重要，因为它允许程序员:

- 动态选择新的对象的大小(从而避免通过数组硬编码限制而导致的程序失败**

- 定义和使用递归数据结构

- 将新创建的对象返回给父过程

- 将一个函数作为另一个函数的结果返回

堆分配的对象通过引用来访问。*通常，引用是指对象的指针*。然而，引用也可以替代性地仅间接地引用一个对象。句柄的优势在于**允许对象被重定位，而无需更改程序内存中该对象/句柄的每个引用**

### 显式释放

任何非平凡的程序，在有限的内存中运行，有时候需要回收不再被计算所需的对象所使用的存储空间。堆对象使用的内存可以通过显式分配，或者由运行时系统自动回收，使用引用计数或者追踪式垃圾收集器。

手动回收会导致以下两种错误的发生:

- 内存可能被过早释放，而此时仍然有引用指向它——这会导致悬空指针的问题

> 检测悬空指针的一种简要的方法是使用胖指针。这些指针可以同来存储它们对目标对象的版本号以及指针本身，然后必须通过检查诸如解引用等操作，以确保指针中存储的版本号与对象的版本号一致。(但是使用这种方式会导致一定的开销，而需要搭配调试工具使用)

- 对于程序中的需要释放的对象因为某种原因忘记释放，导致内存泄漏(Memory Leak**

第二种错误在大型程序上十分常见，尤其是当两个/多个子例程可能持有对对象的引用时。

> 使用自动内存管理可以显著简化并发算法的构建

这个问题比程序员需要更加小心对待，因为这个问题处于更加底层的位置。正确的内存管理的困难往往是固有的——编程的问题在于此。更普遍地来讲，安全地释放一个对象十分复杂

> "活动的特性是全局的，但是决定一个变量是否应该调用free却是局部来控制**

当然，并不是所有的语言都支持自动内存管理，在不受支持的语言中，程序员应该如何应对?

关键建议 : 在管理对象的所有权方面应该保持一致。首先，程序员应该尽可能的完全避免堆分配。其次，程序员应该通过值传递和返回对象，通过复制参数/结果的全部内容，而不是通过传递引用。

> 这两种方式是有代价的，以增加内存压力和失去共享为代价的。在某些情况下，使用自定义分配器可能是适当的。

C++语言已经见过多次尝试使用特殊的指针类和模板来改进内存管理。这些重载了正常的指针操作，以提供安全的内存回收。**但是使用这些智能指针也具有一定的局限性，`auto_ptr`模板不能与标准模板库一起使用，并且在C++17的标准中被移除——被提供更加严格的所有权语义的改进的`unique_ptr`所替代，当`unique`指针时允许目标对象删除**。同时还引入了`shared_ptr`用于共享指针计数。

Rust也提供了类似的库类型，也许在由多个线程使用时自动强制更多的安全性。引用计数的指针无法管理自引用循环数据结构。大多数智能指针则作为库所提供。

如果效率是一个问题，这会限制它们的应用，并且这些指针很适合用于管理一些很少被分配/传递的块，在这种情况下开销会比追踪收集低得多，**另一方面，如果没有编译器和运行时系统的配合，引用计数指针不是管理小对象的高效解决方案，特别是如果指针操作要确保线程安全的情况下**

除此之外，内存安全依旧是一个很大的问题。`Chromium`项目中超过一半的问题都是涉及内存安全，并且使用沙箱并不能解决这类问题

### 自动动态内存管理

这项技术解决了上述提到的大多数的问题，垃圾回收防止创建空悬指针：*只有当从可到达对象中没有指向它的指针时，它才可以被回收*。相反，原则上所有垃圾都会保证被释放——除开两个例外：

1. 追踪收集使用的是一种可判定的“垃圾”定义，可能不包括所有永远不会访问的对象。

2. 垃圾收集器的实现可能会出于效率的原因选择不回收某些对象。而只有收集器会释放对象，这就避免了双重释放问题。**所有的回收决策全部都推迟给收集器，它对堆中对象的结构以及可以访问它们的线程有全局的了解**。显式释放内存的问题主要根源于在本地上下文中做出全局决策的困难。

首先，内存管理是一个软件工程方面的问题。e设计良好的程序是由高度内聚且松散耦合的组件构建而成的。提高模块的内聚性使得程序更易于维护。*理想情况下，程序员应该通过模块的代码就能够理解其行为，或者在最坏情况下，只需要几个少数密切相关的模块就可以理解其行为*。就正确的内存管理而言，这意味着模块不应该需要了解其他模块所使用的内存的管理规则，相比之下，显式内存管理违背了组件之间最小化通信的良好软件工程原则。它会使得接口变得极度混乱。要解决这个问题，要么通过额外的参数显式地传达所有权，要么通过要求程序员遵循特定的惯用法来隐式实现。要求代码理解交战规则会限制组件的可用性和复杂接口。

垃圾回收的关键论点不仅在于它简化了编程——这是它的确做到了——更在于它将内存管理与接口解耦，而不是将其分散到整个代码之中。它提高了可重用性。这就是为什么垃圾回收，以某一种形式或另一种形式，一直是几乎所有现代语言的要求。

对于自动动态内存管理来说，这是一个间接且经济的方法：**各种供应商和内存错误检测工具的持续存在**

> 我们不声称垃圾回收是一个银弹，能够根除所有与内存相关的编程错误，或者它在所有情况下都适用。内存泄漏时最常见的内存错误类型之一。尽管垃圾回收倾向于减少内存泄漏的机会，但它并不能够保证完全消除它们。如果一个对象结构对程序的其余部分变得不可达，那么垃圾收集器将回收它。由于这是对象能够被删除的唯一方式，悬空指针就不会出现。此外，如果一个对象删除导致其子对象变得不可达，那么它也会被回收。因此上述提到的两种错误中的一种基本上在自动动态内存管理中不可能发生。然而对于内存泄漏来说则完全没法保证，因为自动动态内存管理对于以下的问题没有一个确切的答案：**一个仍然可达但是无限增长的数据结构，或者一个可达但是从未被再次访问的数据结构**


### 比较垃圾收集算法

在本书中，我们会着重比较各种收集器，每个收集器针对1不同的工作负载、硬件环境和性能需求进行了设计——这同样说明了收集器没有一个最佳的解决方案。下面首先引入对于收集器的考核指标，虽然在某种程度上来说，这种比较是十分困难的。实现的细节、局部性和算法复杂度公式中的常数的实际意义使得它们不足以被作为实践中的完美指南。更进一步来说，这些指标通常需要组合在一起进行分析，单独看一项是几乎毫无意义的

> 此外，这些指标不是独立变量，算法的性能不仅仅取决于堆中的对象的拓扑结构和数量，还取决于应用程序的访问模式。更糟糕的是，生产虚拟机中的调优选项是相互关联的。为了实现特定目标而忽略其他的参数是往往本末倒置的。

1. 安全

这是首要考虑的一个重要因素，**收集器绝对不能回收活动对象的存储空间**。但是这也是有代价的，特别是对于并发收集器。保守的收集安全性，它既不得到编译器或运行时系统的帮助，原则上可能容易受到某些伪装指针的编译器优化的影响。

2. 吞吐量和消耗的周期

一个常见的用户目标是他们的程序应该运行得更快。然而，这方面有几个因素影响。

 - 垃圾回收所花费的总时间。该项应该越低越好，这在文献中通常被称为**标记/分配比率**。然而，用户最有可能希望整个应用程序尽可能快地执行。在大多数设计良好的配置中，突变器花费的CPU时间比收集器多得多。因此，为了提高突变器的吞吐量，可能值得牺牲一些收集器的性能。
 
- 吞吐量和墙钟时间可能不是这里的唯一指标，特别是在并行和并发收集器的上下文中，这些收集器会投入多个线程进行垃圾回收。不同的收集器可能会消耗非常不同的CPU周期，这些周期本可以用于统一主机上的其他应用程序。

3. 完整性x及时性

理想情况下，垃圾回收应该是完整的：**最终，堆中的所有垃圾都应该被回收**。然而，1这并不总是可能的，甚至可能并不可取[^1]。出于性能原因，可能希望在每个回收周期都不收集整个堆。

[^1]:例如自循环结构，对于纯引用计数无法回收这类引用计数

并发收集器交错执行i突变器和收集器的执行；此类收集器的目标是避免，或者说至少限制对用于程序的干扰。这种行为带来的一个潜在风险在于，在收集周期开始之后，成为垃圾的对象可能要到下一个周期的结束才能被回收。这样的对象一般称之为**浮动垃圾**。*因此，在并发环境下，将完整性定义为所有垃圾的最终回收才可能比较合适，而不是在一个周期内回收*。不同的收集算法在回收的及时性上可能会有所不同，从而要考虑时间/空间均衡

4. 暂停时间和延迟

另一方面，一个重要的要求可能是尽量减少收集器对程序执行的干扰。许多收集器会在收集垃圾时向程序的执行引入暂停，因为它们会暂停所有突变器的线程。显然，使这些暂停尽可能短是可取的。然而，限制暂停时间的机制可能会存在副作用。

最大或平均暂停时间本身不足以作为指标进行衡量。低暂停时间不一定意味着低应用程序延迟。更重要的是，突变器需要取得进展。因此，暂停时间的分布也是很重要的一个参考指标。

5. 空间开销

这是内存管理的主要目标，不同的内存管理器，无论是显式管理还是隐式管理，都会带来不同的空间开销。一些垃圾收集器可能会对每个对象产生空间成本；而另一些垃圾收集器则可以将这些开销隐藏到对象现有的布局中。收集器可能具有每个堆的空间开销。

6. 能量使用

对于计算设备的能量消耗在许多情况下是一个主要关注的问题。虽然减少执行时间往往会减少能量消耗，但是许多因素都会起作用，特别是在并发系统中。

#### 针对特定语言的优化

垃圾回收算法也可以根据它们对不同语言范式的适用性进行表征。函数式语言尤其为与内存管理相关的优化提供了丰富的土壤。

#### 可扩展性和可移植性

这里的最终指标是可扩展性和可移植性。尽量避免依赖硬件以及绑定操作系统。

### 性能劣势？

自动内存管理和手动内存管理的性能比较是一个经常来讨论的话题，一般来说，自动动态内存管理的成本高度依赖于应用程序行为甚至是硬件，因此无法提供简单的开销估计。虽然自动内存管理确实会对程序的性能产生惩罚，但是并不像人们普遍认为的那样严重。此外，手动`malloc()`和`free(**`同样的也会带来显著的成本。

#### 试验方法

目前的内存管理文献试验报告依旧存在大量的不严谨的测试，并且缺乏统计分析，以至于让人怀疑是否可以对结果有任何信心。引入的错误可能是系统性的或者随机的。系统性错误主要归因于不良的实验实践，并且通常可以通过更仔细地设计实验来减少。幸运的是，目前除了用于压力测试之外，之前的测试基准已经被放弃，取而代之的是由广泛使用的程序组成的大规模基准测试套件，这些程序被认为代表了广泛的典型行为。然而，代表企业级应用的基准测试套件的可用性和访问行仍然存在问题。

### 术语与符号

首先，关于存储单位的一个说明，我们采用这样的约定:**一个字节包含八个比特，类似的，使用KB,MB,TB等这些术语来表示字节的相应的2次幂的倍数**。

#### 堆

堆*要么是一个连续的内存字节数组，要么组织成一组不连续的连续字块*。粒度是分配的最小单元，通常是字或者双字，具体取决于对其要求。块*是一大组连续的粒度*。单元*通常是一组较小的连续粒度*，可以是已分配或者空闲的，真实可能由于某种原因而被浪费/无法使用。

一个对象是为应用程序分配的单元格，一个对象通常被认为是连续的、可寻址的字节/数组，分为槽位或者字段。一个字段可以包含一个引用或者某些其他标量非引用值。而一个引用要么是指向堆对象的指针，要么是一个特殊的`nullptr`。


#### 突变器与收集器

遵循Dijkstra等人的规定，一个垃圾回收程序应该被分为两个半独立的部分：

 - 突变器——执行应用程序代码，该代码分配新对象并且通过更改引用字段来改变依赖图，使得这些字段指向不同的目标对象。这些引用字段可能包含在堆对象中，也可能包含在其他被称为根部的地方。因此这种引用更新，任何对象都可能最终与根节点断开连接，也就是说，通过从根开始的任何边的序列都无法到达。
 
 - 收集器执行垃圾回收代码，发现不可达对象并回收他们的存储空间。
 
一个程序可能有多个突变器线程，但是这些线程在通常情况下都可以被视为对堆的一个单一参与者。收集器同理。

#### 突变器根

在堆内存之外，我们假设有一组有限的突变器根，代表存储中持有的指针，这些指针可以直接被突变器访问，而无需通过其他对象。由此延伸，堆中直接由根引用的对象被称之为*根对象*。突变器通过从当前根对象集来加载指针来访问图中的对象(同时还添加新的根)。突变器还可以通过用其他的引用(null或者指向另一个对象的指针**覆盖根指针的存储来丢弃一个根。

> 通常情况下，在实践中，根通常包括静态/全局存储和线程局部存储，其中包含突变器线程可以通过它们直接操作堆对象的指针。随着突变器线程随时间执行，它们的状态将发生变化

在一种类型安全的编程语言中，**一旦一个对象在堆中变得不可达，并且突变器已经丢弃了所有指向该对象的指针，那么突变器就没有办法重新获取该对象的指针**。突变器不能任意地“重新发现”对象——无法遍历到它的任何指针，并且禁止通过算术构造新的指针。

### 引用，字段和地址

在一般情况下，我们将堆节点N通过其内存地址来引用[^2]。给定一个对象N，我们可以通过将对象视为字段数组来引用其任意字段——这些字段可能包含也可能不包含指针

[^2**:尽管这不一定必须是对象的首个字，但可能是对象数据元数据布局中的某个适当的标准点，一般称之为规范指针

### 活性、正确性和可达性

**一个对象如果在突变器的未来执行过程中将被访问，则称其为活动的**。一个垃圾收集器只有在不回收活动对象的情况下才被认为是设计正确的。但是这种性质一般情况下是不可判定的(没有任何办法判断一个任意程序是否会妨碍问特定的堆对象。但是我们可以通过一个相似的可判定属性来判定——指针可达性。

**如果一个对象N可以通过从M的某个字段f开始，沿着指针链进行追踪来访问，则称对象N从M可达**



#### 堆分配器

堆分配器可以认为在功能上与收集器正交，尽管在实践中，某些分配器和收集器实现策略的组合比其他组合更有意义。

分配器支持两种操作：

- 分配，它为对象预留底层内存存储，

- 释放，它将存储返回给分配器以供后续重用。(分配器预留的存储大小可以作为可选参数传递；当省略时，分配是固定大小的对象**

#### 突变器读写操作

在执行过程中，突变器线程若执行若干对于收集器感兴趣的擦欧洲哦：新建，读取和写入。我们通常使用以大写字母开头的命名约定来命名突变器操作，而收集器操作则使用小写字母命名。


## 第二章 标记清除垃圾回收

目前所有的垃圾回收方案都是基于以下四种基本方法之一：**标记-清除收集**、**复制收集**、**标记-压缩收集**、**引用计数**

或者是上述方法的某种组合。

基本假设：*假设突变器正在运行一个或者多个线程，但是只有一个收集器线程。在收集器线程运行时，所有的突变器线程都将会停止*。

手机行为只能在满足以下的条件的位置开始：

- 收集器保证能够找到所有活动对象

- 突变器保证在收集后能够正确恢复

满足上述条件的位置称之为**GC安全点**。突变器将在代码的多个位置检查是否需要收集。这些位置必须包括*对象分配点*和*线程可能挂起的位置*。

这种停止世界的方法极大地简化了收集器的构建。从突变器线程的角度上来看来看，收集似乎是原子执行的：**没有突变器线程会看到收集器中的人和中间状态，而收集器也不会看到突变器线程对其任务的干扰**。


理想的垃圾收集器的目标在于**回收程序中所有将不要再使用的对象所使用的空间**。任何自动内存都有以下三个任务：

- 为新对象分配空间

- 识别存活对象

- 回收已死亡的对象占用的空间

这些人物并非独立任务。特别是，空间回收的方式会影响新鲜空间的分配。

**如果对象能够通过从一组已知根节点出发，沿着引用链到达，我们就接受它作为存活的对象。反之则是死亡的***。这种判定虽然不能保证存活的对象是真的存活，但是能确保死亡的对象一定死亡

### 标记-清除算法

标记-清除算法是对指针可达性的直戳了当的实现。其收集操作分为两个阶段：

- 在第一阶段，收集器遍历对象的图，从根开始，这些根可能是程序直接访问对象的起点，然后沿着指针并标记它找到的每个对象，这种遍历称之为*追踪*

- 第二个为清除阶段，收集器检查堆中的每个对象：**任何未标记的对象都将视为垃圾，并回收其空间**

标记-清除算法是一种间接算法，它本身并不检测垃圾，而是识别所有存活的对象，然后推断出其他所有的对象都是垃圾。

> 请注意，它需要每次调用时重新计算其存活的对象集的估计值。并非所有垃圾回收算法都像这样。

从垃圾收集器的角度上来看，突变器线程仅执行三种值得关注的操作：`New`、`Read`和`Write`，每种手机算法都必须适当地重新定义这些操作。标记-清除算法与突变器之间的接口十分简单，如果线程无法分配对象，则调用收集器并重试该请求。*为了强调收集器以停止世界模式运行，我们将收集例程标记作为原子关键字。如果仍然没有足够的内存来分配请求，会导致堆内存耗尽——这通常是无法接受的一个错误*

在遍历对象图之前，收集器必须首先用遍历的起始点初始化标记器的工作列表。每个根对象都会被标记，然后添加到工作列表之中。


标记-清除算法的分配环节伪代码：

```
New():
    ref<- allocate()
    if ref= null
        collect()
        ref<-allocate()
        if ref=null
            error "Out of memory"
        return ref
        
atomic collect():
   markFromRoots()
   sweep(HeapStart,HeapEnd)
```

标记-清除算法的标记环节的伪代码：
```
markFromRoots():
    initalise(worklist)
       for each fld in Roots
           ref<- *fld
           if ref != null && not isMarked(ref)
               setMarked(ref)
               add(worklist,ref)
               mark()
initalise(worklist):
    worklist<- empty
mark():
    while not isEmpty(worklist)
        ref<- remove(worklist)
        for each fld in Pointers(ref)
        child <- *fld 
        if child != null && not isMarked(child)
            setmarked(child)
            add(worklist,child)
```

标记-清除算法的清除部分的伪代码
```
    sweep(start,end):
        scan <-start
        while scan < end 
        if isMarked(scan)
            unsetMarked(scan)
        else free(scan)
            scan <- nextObject(scan)
```


一个对象可以通过设置一个位来被标记，这个位可以在对象的头部或者辅助表中。如果一个对象不包含指针，那么因为它没有子对象，所以没有必要将它添加到工作列表中。
